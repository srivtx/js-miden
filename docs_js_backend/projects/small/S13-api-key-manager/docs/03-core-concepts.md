# S13 API Key Manager — Core Concepts

## API Key Hashing

API keys are high-entropy secrets generated by the server. Unlike passwords, they are not chosen by humans.

### Why SHA-256?
1. **Entropy**: A 256-bit random key has 2^256 possible values. Brute-forcing is physically impossible.
2. **Speed**: SHA-256 completes in microseconds. bcrypt adds ~100ms latency to every API call.
3. **Lookup**: SHA-256 is deterministic, enabling indexed database lookups.

### Implementation
```typescript
const hash = crypto.createHash('sha256').update(fullKey).digest('hex');
// Store `hash` in DB; return `fullKey` to user exactly once
```

### Verification
```typescript
const hash = crypto.createHash('sha256').update(providedKey).digest('hex');
const row = db.prepare('SELECT * FROM api_keys WHERE key_hash = ?').get(hash);
```

## Timing-Safe Comparison

Standard string comparison (`===`) short-circuits on the first mismatch, leaking timing information:

```typescript
// Vulnerable: leaks length of matching prefix
if (a === b) { ... }
```

### Fix: crypto.timingSafeEqual
```typescript
const providedHash = crypto.createHash('sha256').update(providedKey).digest();
const storedHash = Buffer.from(row.key_hash, 'hex');

if (providedHash.length !== storedHash.length) return false;
if (!crypto.timingSafeEqual(providedHash, storedHash)) return false;
```

**Why it works**: `timingSafeEqual` always compares all bytes, regardless of mismatches. The execution time is constant.

## Key Prefixes

Prefixes serve as metadata without requiring a database lookup:

| Prefix | Meaning |
|--------|---------|
| `pk_live_` | Production key |
| `pk_test_` | Test/sandbox key |
| `sk_live_` | Secret key (server-side only) |

Stripe popularized this pattern. It allows middleware to reject test keys on production endpoints before even hitting the database.

## Key Rotation

Rotation is the process of replacing an old key with a new one without downtime.

### Zero-Downtime Rotation
1. Generate new key.
2. Update client applications to use new key (dual-write period).
3. Monitor logs for usage of old key.
4. Revoke old key once all clients have migrated.

### Database Schema Support
The schema supports multiple active keys per user. There is no "user_id" column in this simplified project, but in production:
```sql
CREATE TABLE api_keys (
  id INTEGER PRIMARY KEY,
  user_id TEXT NOT NULL,
  key_hash TEXT NOT NULL,
  ...
);
```

## Rate Limiting (Sliding Window)

The current implementation uses a fixed 1-minute window per key:
```typescript
const windowStart = Math.floor(Date.now() / 60000) * 60000;
```

### Sliding Window (More Accurate)
Count requests in the last 60 seconds, not just the current minute:
```typescript
const window = Date.now() - 60000;
const count = redis.zcount(`ratelimit:${keyId}`, window, '+inf');
```

**Trade-off**: Fixed window is simpler and sufficient for most APIs. Sliding window prevents burst attacks at window boundaries.
