# CONCEPTS: Config Manager

## Concept 1: Atomic File Operations

### WHAT

An atomic operation is one that either completes entirely or not at all, with no intermediate state visible to observers.

### WHY

If a process crashes during a file write, a non-atomic operation leaves the file in a partially-written state. The next read gets invalid JSON, and the application can't start.

### HOW

```typescript
// WRONG: Direct write (non-atomic)
async function saveDirect(path: string, data: object): Promise<void> {
  const json = JSON.stringify(data, null, 2);
  await fs.writeFile(path, json); // Crash here = corrupted file
}

// RIGHT: Write to temp + rename (atomic on POSIX)
async function saveAtomic(path: string, data: object): Promise<void> {
  const json = JSON.stringify(data, null, 2);
  const tmpPath = `${path}.tmp`;
  await fs.writeFile(tmpPath, json);
  await fs.rename(tmpPath, path); // Atomic: old file OR new file, never both
}
```

### WRONG vs RIGHT

**WRONG: Direct write**
```typescript
await fs.writeFile('config.json', json);
// Process crashes here -> config.json is partially written or empty
```

**RIGHT: Temp file + rename**
```typescript
await fs.writeFile('config.json.tmp', json);
await fs.rename('config.json.tmp', 'config.json');
// Process crashes at any point:
// - Before writeFile: config.json unchanged
// - During writeFile: config.json.tmp may be partial, config.json unchanged
// - During rename: config.json unchanged (rename is atomic)
// - After rename: config.json is complete
```

## Concept 2: Type Validation at Write Time

### WHAT

Validating configuration values when they are written, not when they are read.

### WHY

Fail fast. If a value is invalid, reject it immediately. Don't let invalid data propagate through the system and cause a crash hours later in an unrelated module.

### HOW

```typescript
class ConfigManager {
  private schemas: Map<string, { type: string }> = new Map();

  addSchema(key: string, schema: { type: string }): void {
    this.schemas.set(key, schema);
  }

  private validate(key: string, value: any): void {
    const schema = this.schemas.get(key);
    if (!schema) return; // No schema = anything goes

    if (typeof value !== schema.type) {
      throw new Error(
        `Expected ${schema.type} for ${key}, got ${typeof value}`
      );
    }
  }

  async set(key: string, value: any): Promise<void> {
    this.validate(key, value); // Validate BEFORE saving
    this.cache.set(key, value);
    await this.save();
  }
}
```

### WRONG vs RIGHT

**WRONG: Validate at read time**
```typescript
// config.json contains: { "port": "8080" }

// Later, in server startup:
const port = config.get('port');
server.listen(port); // TypeError: "8080" is not a number
// Crash! But the bug was introduced hours ago.
```

**RIGHT: Validate at write time**
```typescript
await manager.set('port', '8080');
// Error: Expected number for port, got string
// Bug caught immediately at the source
```

## Concept 3: Configuration Hierarchy

### WHAT

Configuration values come from multiple sources with defined precedence.

### WHY

Different environments (dev, staging, prod) need different values. Secrets shouldn't be in code. Defaults should work out of the box.

### HOW

```
Priority (highest to lowest):

1. Command-line arguments
   node server.js --port=9000
   
2. Environment variables
   PORT=9000 node server.js
   
3. Environment-specific config file
   config.production.json
   
4. Base config file
   config.json
   
5. Code defaults
   const port = config.get('port') ?? 3000;
```

### WRONG vs RIGHT

**WRONG: Single config file for all environments**
```typescript
// config.json in repo
{ "db_host": "localhost" }

// In production, someone edits the file directly
// File changes are overwritten on next deploy
```

**RIGHT: Layered configuration**
```typescript
// config.json (committed to repo)
{ "db_host": "localhost", "port": 3000 }

// config.production.json (generated by CI/CD)
{ "db_host": "prod-db.internal", "port": 80 }

// Environment variable (set by ops)
DATABASE_URL=postgresql://prod-db.internal:5432/app

// Merge: env vars override file configs
```

## Concept 4: Hot Reload vs Restart

### WHAT

Hot reload means applying configuration changes without restarting the application.

### WHY

Restarting takes time (seconds to minutes) and can drop connections. Hot reload allows instant configuration updates with zero downtime.

### HOW

```typescript
// File watcher approach
import { watch } from 'fs';

watch(configPath, () => {
  console.log('Config changed, reloading...');
  manager.load();
});

// Or polling approach (simpler, more portable)
setInterval(() => manager.load(), 5000);
```

### WRONG vs RIGHT

**WRONG: Restart on every config change**
```bash
# Edit config.json
# Restart server (dropping all connections)
pm restart
```

**RIGHT: Watch file and reload**
```typescript
watch(configPath, debounce(() => {
  manager.load().catch(err => {
    logger.error('Failed to reload config:', err);
    // Keep running with old config, don't crash
  });
}, 100));
```
