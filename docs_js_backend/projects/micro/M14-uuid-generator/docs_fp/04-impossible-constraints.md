# M14 UUID Generator: Impossible Constraints

## The Challenge

Implement UUID v4 generation **without** using:

- `crypto.randomUUID()`
- `crypto.randomBytes()`
- The `uuid` npm package
- Any external randomness library

You may only use:

- `crypto.createHash('sha256')`
- `process.hrtime.bigint()`
- `process.pid`
- `Math.random()` (but only for non-security padding, not for the core entropy)

And you must still produce RFC 4122-compliant UUID v4 strings.

## Why This Is Hard

`crypto.randomBytes` reads from the OS CSPRNG, which is seeded with hardware entropy (keyboard timings, disk noise, thermal noise). Without it, you must construct your own entropy pool from deterministic but high-variance sources. Then you must format the 128 bits correctly:

1. **Entropy construction**: Combine high-resolution time, process ID, and a hash to create unpredictable seed material.
2. **Version nibble**: Force bits 48-51 to `0100` (hex `4`).
3. **Variant nibble**: Force bits 64-67 to `10xx` (hex `8`, `9`, `a`, `b`).
4. **Hex formatting**: Convert 16 bytes to a 36-character hyphenated string.

## The Constraint Set

| Constraint | Implication |
|------------|-------------|
| No randomBytes | You construct entropy from time + pid + hash |
| No randomUUID | You implement the bit layout yourself |
| Must be RFC 4122 compliant | Version and variant bits must be exact |
| Must validate with strict regex | `/^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i` |
| Must not be sequential | Two calls in a loop must produce different UUIDs |

## Hints (Hidden)

<details>
<summary>Click to reveal</summary>

1. Build an entropy string from multiple high-variance sources:
   ```javascript
   const entropy = `${process.hrtime.bigint()}-${process.pid}-${Math.random()}-${Date.now()}`;
   ```

2. Hash the entropy to produce 16 deterministic-but-unpredictable bytes:
   ```javascript
   const hash = crypto.createHash('sha256').update(entropy).digest();
   const bytes = hash.slice(0, 16);
   ```

3. Set version and variant:
   ```javascript
   bytes[6] = (bytes[6] & 0x0f) | 0x40;
   bytes[8] = (bytes[8] & 0x3f) | 0x80;
   ```

4. Format:
   ```javascript
   const hex = bytes.toString('hex');
   return `${hex.slice(0,8)}-${hex.slice(8,12)}-${hex.slice(12,16)}-${hex.slice(16,20)}-${hex.slice(20,32)}`;
   ```

5. **Why this is insecure for production**: An attacker who knows the exact system time and process ID can reproduce the hash input and predict the UUID. This exercise proves why `crypto.randomBytes` is necessary.

## Why This Is Worth Doing

This is exactly what early UUID libraries did before OS CSPRNGs were universally available. By rebuilding it, you understand:

- Why entropy quality matters: `Date.now()` + `Math.random()` is predictable. `process.hrtime.bigint()` adds nanosecond variance.
- Why hashing is not randomization: A hash of predictable inputs is deterministic. It is not a substitute for a CSPRNG.
- Why the version and variant bits exist: They are not decorative. They prove the UUID was generated by a compliant algorithm.

You are not reinventing the wheel. You are proving why the wheel needs rubber.
