# M03 Health Check: Red Team

## Attack Scenarios

Health checks are trusted by infrastructure. If an attacker can manipulate a health check, they can manipulate the infrastructure. Here is how.

---

## Attack 1: The Slowloris Health Check

### The Vector

Your readiness probe checks the database with a query like `SELECT 1`. The attacker finds a way to make the database slow for your application user but not for others. For example, they fill the connection pool with idle connections from your application's credentials.

### The Exploit

The readiness probe times out. The orchestrator marks the pod as not ready. The load balancer stops routing traffic to it. The attacker does this to every pod, one by one. The entire cluster is marked not ready. The load balancer returns `503` for all traffic. The attacker has caused a Denial of Service without sending a single request to the public endpoint.

### The Defense

1. **Use separate credentials for health checks**. The health check user should have a tiny connection pool and a `statement_timeout` of 1 second.
2. **Add a query timeout in the application**:
   ```javascript
   await db.query('SELECT 1', { timeout: 1000 });
   ```
3. **Rate-limit health check failures**. If a pod fails readiness 10 times in 60 seconds, investigate. Do not blindly drain it.
4. **Monitor the database separately**. A database slowdown should trigger a database alert, not a cascade of pod restarts.

---

## Attack 2: The Fake Healthy Response

### The Vector

The attacker gains code execution in your container (via a dependency vulnerability). They modify the health check endpoint:

```javascript
app.get('/health', (req, res) => {
  res.json({ status: 'ok' });
});
```

It now returns `200` regardless of actual health.

### The Exploit

The application is broken. The database connection pool is exhausted. The cache is unreachable. But `/health` returns `200`. The orchestrator thinks everything is fine. The load balancer keeps routing traffic. Customers see errors. The attacker has created a silent failure mode where the infrastructure believes the system is healthy while it is actively failing.

### The Defense

1. **Do not run health checks inside the application process**. Use an external sidecar or exec probe that checks the process from the outside.
2. **Sign health check responses**. The orchestrator verifies a cryptographic signature on the health response to ensure it was generated by unmodified code.
3. **Monitor business metrics independently**. Error rate, latency, and throughput should alert even if health checks pass.

---

## Attack 3: The Health Check Information Leak

### The Vector

Your deep health check returns detailed dependency information:

```json
{
  "status": "healthy",
  "database": {
    "host": "postgres.internal:5432",
    "version": "PostgreSQL 14.2",
    "ssl": false,
    "latencyMs": 12
  },
  "cache": {
    "host": "redis.internal:6379",
    "version": "Redis 6.2",
    "keys": 48291,
    "latencyMs": 3
  }
}
```

### The Exploit

The attacker probes `/health` before attacking. They learn:
- The exact database version (look up CVEs for PostgreSQL 14.2).
- That SSL is disabled (man-in-the-middle is possible).
- The internal hostnames (map the network).
- The cache has 48,291 keys (estimate data volume and memory usage).

This is reconnaissance. The attacker uses your health check as an intelligence gathering tool.

### The Defense

1. **Do not expose `/health` publicly**. Bind it to `localhost` or an internal port. Use a reverse proxy to block external access.
2. **Return minimal information on the readiness probe**. The readiness probe should return `200` or `503`. Nothing else.
3. **Put deep health checks behind authentication**. Only operators with internal credentials should access detailed dependency status.
4. **Obfuscate versions and hostnames**. Return generic names like `db-primary` and `cache-cluster`.

---

## Red Team Summary

| Attack | Impact | Defense |
|--------|--------|---------|
| Slowloris health check | DoS via infrastructure drain | Separate health check credentials, timeouts, rate limits |
| Fake healthy response | Silent failure, traffic routed to broken pods | External probes, signed responses, business metric alerts |
| Information leak | Reconnaissance for targeted attacks | Internal-only endpoints, minimal responses, authentication |

## The Meta-Attack

The most dangerous attacker does not attack your health check. They attack the **trust model** between your application and your infrastructure. If the infrastructure blindly trusts the application to report its own health, the attacker who compromises the application compromises the infrastructure's decision-making. The health check is not a security boundary. It is a reporting channel. Treat it with the same suspicion you treat any other user input.
